# 第 1 章 補　Snowflake そのものの動きを体感する

所要時間の目安: 12 分
実行するロール: ACCOUNTADMIN
使うファイル: `sql/step1b_basics.sql`（ワークスペースの左側の一覧から開きます）

---

## 1. この章は何のためにあるのか

第 2 章から先は「放送視聴データをどう組み立てるか」という中身の話に入ります。
dbt でモデルを書き、セマンティックビューを作り、エージェントに聞く、という流れです。

その中身の話に入ってしまうと、土台側の話で立ち止まりにくくなります。
そこでこの章では、Snowflake という土台そのものが持っている性質を 4 つだけ、
先に手で触っておきます。

扱うのは、初めて触った人がいちばん驚く順に並べた 4 つです。

| 触るもの | 何が分かるか |
| --- | --- |
| ウェアハウスのサイズ変更 | 計算する機械とデータが分かれている |
| 結果キャッシュ | 同じクエリは機械を動かさずに返る |
| UNDROP | 消したテーブルが 1 行で戻る |
| Time Travel | 消していないが壊した場合も戻せる |
| ゼロコピークローン | 大きなテーブルが一瞬で、容量を増やさず複製できる |

どれも設定は必要ありません。アカウントを作った時点で効いています。

---

## 2. 何を実行するのか

`sql/step1b_basics.sql` を上から順に実行します。全部で 5 節です。

### 2-1　ウェアハウスの大きさと処理時間

同じクエリを 2 回実行します。1 回目は XSMALL、2 回目は LARGE です。

実行するクエリは、視聴区間を 1 分単位に分解しながら、
毎分・局ごとの視聴受信機数を数えるものです。
105 万行の視聴区間が 1,212 万行に膨らみ、そこから重複しない受信機を数えるので、
それなりに計算量があります。

この分解は、第 2 章で dbt が作る `int_viewing_minutes` と同じ考え方です。
つまりこの節は、第 2 章の内容の先取りにもなっています。

**手順**

1. `ALTER WAREHOUSE ... SET WAREHOUSE_SIZE = 'XSMALL';` を実行
2. `ALTER SESSION SET USE_CACHED_RESULT = FALSE;` で比較中の結果キャッシュを止める
3. 集計クエリを実行し、**実行時間を書き留める**（Snowsight の結果パネルに Duration として出ます）
4. `ALTER WAREHOUSE ... SET WAREHOUSE_SIZE = 'LARGE';` を実行
5. **まったく同じクエリ**を実行し、時間を比べる

比較中だけ結果キャッシュを止めないと、LARGE 側が XSMALL の前回結果を返し、サイズ差を正しく測れません。

**確認してほしいこと**

- 3 の `ALTER WAREHOUSE` が一瞬で終わること。データは 1 行も動いていません
- 停止時間がないこと。テーブルを作り直したり、索引を張り直したりしていません

**サイズと料金の関係**

XSMALL から LARGE は 4 段階です。1 段上がるごとに計算資源が 2 倍なので 16 倍、
1 時間あたりの料金も 16 倍になります。

ただし、速くなった分だけ短時間で終わります。同じ仕事を 16 分の 1 の時間で
終えられるなら、支払う額は同じです。実際には 16 倍ぴったりには速くならないので、
そのずれを見てもらうのがこの節の狙いです。

### 2-2　結果キャッシュ

`ALTER SESSION SET USE_CACHED_RESULT = TRUE;` で結果キャッシュを戻してから、
3 度目に**1 文字も違わない同じクエリ**を実行します。ほぼ 0 秒で返ります。

同じクエリで、参照しているテーブルが 1 行も変わっていない場合、
Snowflake は前回の結果をそのまま返します。ウェアハウスは 1 秒も動きません。

- 保持は 24 時間。使われるたびに延びます
- アカウント全体で共有されます。**ウェアハウスをまたぎ、ユーザーをまたいで効きます**
- 元のテーブルが 1 行でも変わると無効になります

第 5 章で作るアプリのように、同じ集計を多くの人が見る画面では、
これがそのまま効きます。

この節の最後で、ウェアハウスを XSMALL に戻します。
**戻し忘れると以降のすべてのクエリが 16 倍の料金で動く**ので、忘れないでください。

### 2-3　消してしまったテーブルを元に戻す（UNDROP）

ここからは事故の話です。視聴ログを 1 つ、うっかり削除してしまった状況を作ります。

```sql
SELECT COUNT(*) FROM VIEWING_LOG_NW01;   -- 行数を覚えておく
DROP TABLE VIEWING_LOG_NW01;             -- 消す
SHOW TABLES LIKE 'VIEWING_LOG_NW01';     -- 0 行なら消えている
UNDROP TABLE VIEWING_LOG_NW01;           -- 戻す
SELECT COUNT(*) FROM VIEWING_LOG_NW01;   -- 行数が一致することを確認
```

3 行目はエラーを出さず、存在するテーブルだけを探します。結果が 0 行なら正常です。
`DESCRIBE TABLE` でも消えたことは確認できますが、エラーでファイル全体の実行が
止まるため、この教材では `SHOW TABLES` を使います。

**なぜ戻るのか**

バックアップから復元したのではありません。Snowflake は変更のたびに
古い状態を保持しているので、消した直後のテーブルはまだ内部に残っています。

- このアカウント（トライアル）の保持期間は 1 日です
- Enterprise 以上では最大 90 日まで設定できます
- DATABASE や SCHEMA も同じように `UNDROP` できます

### 2-4　消していないが中身を壊した場合（Time Travel）

`UNDROP` は「消した」ときの話です。実務でより多いのは、
`WHERE` を書き忘れた `UPDATE` や `DELETE` で、
テーブルは残っているが中身が変わってしまった、という事故です。

この場合はテーブル名のうしろに `AT` を付けて、過去の時点を読みます。

```sql
DELETE FROM VIEWING_LOG_NW01;                              -- 事故
SELECT COUNT(*) FROM VIEWING_LOG_NW01 AT(OFFSET => -300);  -- 5 分前を読む
INSERT INTO VIEWING_LOG_NW01
  SELECT * FROM VIEWING_LOG_NW01 AT(OFFSET => -300);       -- 書き戻す
```

`OFFSET` は秒数です。ほかに、時刻で指定する `AT(TIMESTAMP => ...)` や、
「あのクエリの直前」を指す `BEFORE(STATEMENT => 'クエリID')` も使えます。

要点は、**壊した本人が、誰にも頼まず、SELECT 文の書き方だけで復旧できる**ことです。

### 2-5　コピーせずに複製する（ゼロコピークローン）

第 2 章から変換処理を書き始めます。本番のデータを触りながら試すのは避けたいので、
検証用の複製が欲しい、という場面です。

```sql
CREATE OR REPLACE TABLE VIEWING_LOG_NW01_DEV CLONE VIEWING_LOG_NW01;
UPDATE VIEWING_LOG_NW01_DEV SET CHANNEL_CODE = '999';   -- 複製だけ書き換える
```

複製は一瞬で終わります。行をコピーしていないためです。
作られたのは「同じデータを指す新しい名前」で、追加のストレージはゼロです。
書き換えた部分だけが、あとから実データとして増えていきます。

DATABASE 単位でもクローンできます。
本番データベースをそのまま複製して検証環境にする、という使い方が現実的にできます。
容量が 2 倍にならないので、遠慮なく作れます。

## 3. この章が終わると何ができているか

データそのものは、章の最初と同じ状態に戻っています。
作った複製は最後に片付け、ウェアハウスのサイズも XSMALL に戻しています。

残るのは、次の 5 つを実際に手で確かめた、という経験だけです。

- 重い処理を流す間だけ機械を大きくして、終わったら戻せる
- 同じ集計を多人数が見る画面は、勝手に速くなっている
- 消しても戻る
- 壊しても戻る
- 検証環境は容量を増やさずに作れる

第 2 章から先は、この土台の上に放送視聴データの変換を作っていきます。

## 4. SE Tips

- **サイズ変更は実行中のクエリには効きません。** `ALTER WAREHOUSE` の後に投げた
  クエリから新しいサイズになります。走っているクエリを速くすることはできません。
- **スケールアップとスケールアウトは別ものです。** サイズを上げるのは
  1 つのクエリを速くするため（スケールアップ）。
  `MAX_CLUSTER_COUNT` を上げるのは、同時に来るクエリを待たせないため
  （スケールアウト）です。混同されやすい点です。
- **結果キャッシュはクエリ文字列の完全一致で効きます。** 空白やコメントの
  違いでも別のクエリと見なされます。逆に `CURRENT_TIMESTAMP()` のような
  実行ごとに変わる関数が入っていると、絶対に効きません。
- **Time Travel の保持期間はストレージ料金に効きます。** 変更が多いテーブルで
  保持期間を長くすると、古い版の分だけ容量が増えます。既定値のままでよいか、
  テーブル単位で `DATA_RETENTION_TIME_IN_DAYS` を調整するかは設計事項です。
- **クローンは作った瞬間から独立します。** 元のテーブルをあとから変更しても
  クローンには反映されません。「同じものを指し続ける」わけではない点に注意します。
