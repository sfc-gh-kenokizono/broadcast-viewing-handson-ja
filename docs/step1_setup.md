# 第 1 章 セットアップとデータの取り込み

所要時間の目安 15 分

## 目的

これから使う入れ物を作り、GitHub リポジトリにある CSV を Snowflake に読み込みます。

この章でやることは 4 つです。

1. ロールを 2 つ作る。生データまで見られる人と、集計データだけ見られる人に分けます
2. データベースと 4 つのスキーマを作る
3. GitHub リポジトリに接続する
4. CSV を読み込み、生データのままでは使えないことを確認する

4 つめが地味ですが大事なところです。届いたデータには、そのままでは集計に使えない行が混ざっています。それを目で見てから第 2 章のクレンジングに進みます。

[sql/step1_setup.sql](../sql/step1_setup.sql)

## 書き換えが必要な 3 か所

実行する前に、ファイル内の 3 か所を書き換えてください。

| 場所 | 書き換える内容 |
|---|---|
| `CREATE OR REPLACE SECRET` の `USERNAME` | GitHub のユーザー名 |
| `CREATE OR REPLACE SECRET` の `PASSWORD` | GitHub の個人アクセストークン |
| `API_ALLOWED_PREFIXES` と `ORIGIN` の URL | リポジトリを置いている GitHub のユーザー名または組織名 |

個人アクセストークンの作り方は、GitHub の Settings から Developer settings、Personal access tokens と進み、このリポジトリの読み取り権限だけを付けたトークンを発行してください。

## 層の分け方について

作成するスキーマは 4 つです。

| スキーマ | 役割 | 誰が触るか |
|---|---|---|
| `RAW` | 受け取ったままの原本。加工しない | パイプラインだけ |
| `STG` | クレンジング済み | パイプラインだけ |
| `INT` | ID の名寄せ、番組枠との結合、1 分単位への分解 | パイプラインだけ |
| `MART` | 指標の算出。可視化やエージェントが参照する | 利用者 |

生データを含む層は限られた人だけが見られるようにし、集計済みの層は広く使えるようにします。この差は第 6 章で実際に確認します。

## GitHub との接続について

非公開リポジトリなので、認証情報を Snowflake の中にシークレットとして登録し、API 統合からそのシークレットを使えるようにします。

```
シークレット（認証情報）
    ↑ 参照
API 統合（接続先の URL を許可する）
    ↑ 参照
Git リポジトリ（リポジトリの中身をステージとして扱えるようにする）
```

シークレットに入れた値は、登録したあとに SQL から取り出すことはできません。取り出せないままコードから使える、という形になっています。

接続できたかどうかは次で確認できます。

```sql
LS @BCAST_VIEWING_HANDSON.INTEGRATIONS.BCAST_REPO/branches/main/data/;
```

CSV のファイル名が並べば成功です。

## 生データをそのまま使うと困ること

スクリプトの最後にある 2 つのクエリで、届いたデータの状態を確認します。

### 1. 成立していない行が混ざっている

```
全行数              1,050,648
終了が開始より前          200
視聴が24時間を超える      148
重複した行                300
```

終了時刻が開始時刻より前になっている行、1 日を超えて視聴し続けている行、まったく同じ内容が複数届いている行があります。これらを含めたまま集計すると、視聴時間の合計がおかしくなったり、同じ人を二重に数えたりします。

局ごとに個別のクレンジングを用意するのではなく、同じ定義でまとめて処理する形にします。それを第 2 章でやります。

### 2. 一部の局のデータが届かない日がある

```
NETWORK_ID  視聴日        件数
NW01        2026-07-17    2,7xx
NW02        2026-07-17    3,3xx
NW04        2026-07-17      7xx
NW05        2026-07-17      9xx
```

`NW03` の 7 月 17 日の行がありません。5 つの局からデータを集める仕組みでは、どこか 1 局が遅れたり落ちたりすることが必ず起こります。そのときに全体を止めるのか、届いた分だけで表示を続けるのかは、設計上の判断になります。

## この章で使ったクレジット

```sql
SELECT
  QUERY_TYPE                                   AS 種別,
  COUNT(*)                                     AS 実行回数,
  ROUND(SUM(TOTAL_ELAPSED_TIME) / 1000, 1)     AS 合計秒数,
  ROUND(SUM(CREDITS_USED_CLOUD_SERVICES), 6)   AS クラウドサービスのクレジット
FROM SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY
WHERE WAREHOUSE_NAME = 'BCAST_HANDSON_WH'
  AND START_TIME >= DATEADD('hour', -1, CURRENT_TIMESTAMP())
GROUP BY QUERY_TYPE
ORDER BY 合計秒数 DESC;
```

`ACCOUNT_USAGE` の反映には少し時間がかかります。すぐに見たい場合は Snowsight の Monitoring からクエリ履歴を確認してください。
