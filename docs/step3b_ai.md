# 第 3 章 補　AI 関数でテキストを数字の隣に並べる

所要時間の目安: 12 分
実行するロール: ACCOUNTADMIN
使うファイル: `sql/step3b_ai_functions.sql`（ワークスペースの左側の一覧から開きます）

---

## 1. この章は何のためにあるのか

ここまで扱ってきたのは、行と列に収まっている数字と符号でした。
受信機の ID、視聴の開始時刻、接触回数。すべて集計できる形をしています。

一方、実務のデータには**文章の列**が混ざります。
このハンズオンのデータでは、コマーシャル素材の説明文がそれです。

```
CM0001  みなみ野ビバレッジ  清涼飲料
        夏の屋外で炭酸飲料を飲み、爽快な表情を見せる 15 秒の映像です。
        若い世代に向けた明るいトーンで、商品名を最後に大きく表示します。
```

「商品カテゴリ」は列として持っています。だから `GROUP BY CATEGORY` ができます。
しかし「**誰に向けた表現なのか**」は、説明文の中にしか書かれていません。
訴求軸という列は存在しないので、「訴求軸ごとのリーチ」は出せません。

従来はここで人が目視で分類し、スプレッドシートに転記していました。
この章では、その分類を SQL の中でやります。

- データを外に持ち出しません
- モデルを用意しません。学習もしません
- 権限は既存のロールのままです
- 返ってくるのは普通の列なので、そのまま `GROUP BY` や `JOIN` の材料になります

---

## 2. 使う関数は 3 つ

| 関数 | 何をするか | 1 行に対して |
| --- | --- | --- |
| `AI_CLASSIFY` | 決めた選択肢のどれに当たるかを判定する | 1 つの答え |
| `AI_EXTRACT` | 文章の中に書かれている内容を項目ごとに取り出す | 1 つの答え |
| `AI_AGG` | `GROUP BY` でまとめた複数行の文章を読んで要約する | グループごとに 1 つ |

前の 2 つは `SUBSTR` や `UPPER` と同じスカラー関数、
`AI_AGG` は `SUM` や `AVG` と同じ集約関数です。

### 費用について

AI 関数の費用は、処理した文字数（トークン数）で決まります。
この章で処理するのは 20 行、1 行あたり 100 文字程度なので、ほぼかかりません。

同じ関数を 100 万行に流すときは、**まず `LIMIT` を付けて数十行で試す**のが基本です。
判定の質を確かめてから全件に広げます。

---

## 3. 何を実行するのか

`sql/step3b_ai_functions.sql` を上から順に実行します。

### 3-0　素材になる文章を見る

まず相手を見ます。20 件のコマーシャル素材に、それぞれ説明文が付いています。

### 3-1　文章を分類する（AI_CLASSIFY）

**まず 1 件で試します。**

```sql
SELECT AI_CLASSIFY(
  '夏の屋外で炭酸飲料を飲み、爽快な表情を見せる 15 秒の映像です。若い世代に向けた明るいトーンで、商品名を最後に大きく表示します。',
  ['若年層向け', '家族向け', '健康志向', '高級感', '安心・安全']
);
```

返ってくるのは `{"labels": ["若年層向け"]}` です。
選択肢を配列で渡すだけで、判定の基準を教える作業はありません。

**次に 20 件すべてを、複数ラベルで分類します。**

```sql
AI_CLASSIFY(
  CREATIVE_DESC,
  ['若年層向け', '家族向け', '健康志向', '高級感', '安心・安全', '価格訴求'],
  {
    'output_mode': 'multi',
    'task_description': 'テレビコマーシャルの素材説明文から、その素材がどの訴求軸を使っているかを判定してください'
  }
):labels
```

- `output_mode` を `multi` にすると、当てはまるものを**全部**返します
- `task_description` は何を判定させたいのかの説明です。省略できますが、書いたほうが精度が上がります
- `labels` が配列なので `ARRAY_TO_STRING` で見やすく並べています

**確認してほしいこと**

結果は説明文と訴求軸を左右に並べて出しています。
1 行ずつ、納得できる判定になっているか確かめてください。

人が読んで違うと思う行があれば、それが AI 関数の限界です。
選択肢の言葉を変える、`task_description` を具体的にする、といった調整で
だいたい寄せられます。**判定が常に正しい前提では使いません。**

### 3-2　文章から項目を取り出す（AI_EXTRACT）

分類は「決めた選択肢のどれか」を選ばせるものでした。
こちらは「文章の中に書かれている内容そのもの」を項目ごとに取り出します。

```sql
AI_EXTRACT(
  text => CREATIVE_DESC,
  responseFormat => {
    '登場人物':     '誰が登場しますか',
    '舞台':         'どこが舞台ですか',
    '訴求ポイント': '何を訴求していますか'
  }
)
```

質問を key と value の形で渡すと、その形で答えが返ります。
**どういう答えが返るかをこちら側で決められる**のが要点です。

返る形は `{"error": ..., "response": {...}}` なので、
欲しい項目は `x:response:"項目名"` で取り出します。
日本語の key は二重引用符で囲みます。

1 回の呼び出しで 3 項目まとめて取れるので、
項目ごとに 3 回呼ぶより費用も時間も少なくて済みます。

### 3-3　複数の文章をまとめて要約する（AI_AGG）

ここまでは 1 行に 1 つの答えを返す使い方でした。
`AI_AGG` は集約関数です。`GROUP BY` でまとめた複数行の文章を読んで、
グループごとに 1 つの答えを返します。

```sql
SELECT
  CATEGORY,
  COUNT(*),
  AI_AGG(
    CREATIVE_DESC,
    'これらはテレビコマーシャルの素材説明文です。この商品カテゴリの素材に共通する表現の傾向を、日本語で 2 文以内にまとめてください。'
  )
FROM CM_MASTER
GROUP BY CATEGORY;
```

**SQL で書けなかったのはここです。**
文章を 20 件読んで傾向をまとめる処理に相当する集約関数は、これまで存在しませんでした。

第 2 引数が指示文です。「2 文以内」「日本語で」のように出力の形を指定できます。
ここを変えるだけで、同じデータから別の観点の要約が出せます。

**関連する関数**

- `AI_SUMMARIZE_AGG` — 要約だけが目的ならこちら。指示文を取らない代わりに書くことが少ない
- `AI_SENTIMENT` — **このデータには使いません。** 素材の説明文は制作側が書いた説明であって、誰かの意見や感想ではないため、点数を付けても読み方がありません。視聴者アンケートや問い合わせ履歴があれば、そこが出番になります

### 3-4　AI が作った列を、リーチの数字と突き合わせる

**ここがこの章の目的です。**

訴求軸という列が手に入ったので、第 2 章で作った `MART_FREQUENCY` の
リーチとフリークエンシーを、訴求軸ごとに見られるようになります。

**まず判定結果をテーブルにします。**

```sql
CREATE OR REPLACE TABLE MART.CM_CREATIVE_TAGS AS
SELECT CM_ID, ADVERTISER, CATEGORY, CREATIVE_DESC,
       AI_CLASSIFY(...):labels::ARRAY AS APPEAL_AXES
FROM CM_MASTER;
```

なぜ一度テーブルに落とすのか。
AI 関数は呼ぶたびに費用と時間がかかります。結合のたびに呼び直すのは無駄なので、
判定結果は一度テーブルにして、以降はそれを参照します。
これは AI 関数に限らず、**重い計算を含む列の扱い方の基本**です。

**次に突き合わせます。**

1 つの素材に訴求軸が複数付いているので、`LATERAL FLATTEN` で
1 行 1 訴求軸に開いてから集計します。

```sql
FROM MART.CM_CREATIVE_TAGS t
INNER JOIN MART.MART_FREQUENCY f ON t.CM_ID = f.CM_ID
, LATERAL FLATTEN(INPUT => t.APPEAL_AXES) ax
GROUP BY ax.VALUE::STRING
```

**結果の読み方**

訴求軸ごとに、どれだけの受信機に何回届いたかが並びます。
ここまで来ると「家族向けの表現はリーチが広いが回数が少ない」といった比較ができます。
**もともとデータに無かった軸での比較**です。

注意点が 2 つあります。

- 同じ素材が複数の訴求軸に数えられます。**合計しても全体には一致しません**
- これは表現と接触の関係であって、効果ではありません。
  その訴求軸が売上につながったかは、このデータには入っていません

## 4. この章が終わると何ができているか

- `MART.CM_CREATIVE_TAGS` — 素材ごとの訴求軸を持つテーブル
- 訴求軸ごとのリーチ・フリークエンシー・インプレッションの一覧

そして、文章の列を集計可能な列に変える手順を、3 つの関数で押さえた状態になります。

次の第 4 章では、これらの関数を人が書くのではなく、
質問に応じてエージェントが自分で選んで使う形にしていきます。

## 5. SE Tips

- **`SNOWFLAKE.CORTEX.*` は使いません。** `SNOWFLAKE.CORTEX.COMPLETE` や
  `SNOWFLAKE.CORTEX.SENTIMENT` といった旧い書き方は非推奨で、2026 年末までに
  廃止予定です。現在は `AI_COMPLETE` `AI_SENTIMENT` のように接頭辞なしで書きます。
  古い記事や社内資料に旧い書き方が残っていることがあるので、注意してください。
- **選択肢は 20 個までを目安に。** 公式ドキュメントでも、20 を超えると
  精度が落ちる可能性があるとされています。多すぎる場合は 2 段階に分けます。
- **選択肢の言葉は具体的にします。** 「カテゴリ 1」のような無意味な名前や、
  互いに重なる選択肢を並べると精度が落ちます。
- **`AI_CLASSIFY` は英語を前提に設計されています。** ドキュメントでも
  英語の平文が推奨です。ただし今回のように日本語でも実用的に判定できます。
  精度が出ない場合は、選択肢だけ英語にして表示時に日本語へ戻す手もあります。
- **エラーは NULL で返ります。** 既定では、処理できなかった行は NULL になり、
  クエリ全体は止まりません。原因を知りたい場合は `return_error_details => TRUE`
  を付けると、エラーメッセージ込みのオブジェクトが返ります。
- **費用はトークン数で決まります。** `task_description` や選択肢の説明文も
  入力トークンに含まれるので、全件に流す前に `AI_COUNT_TOKENS` で
  見積もっておくと安全です。
