# 第 1a 章 セットアップとデータの取り込み

所要時間の目安 15 分

## 目的

これから使う入れ物を作り、GitHub リポジトリにある CSV を Snowflake に読み込みます。

この章でやることは 4 つです。

1. ロールを 2 つ作る。生データまで見られる人と、集計データだけ見られる人に分けます
2. データベースと 5 つのスキーマを作る
3. GitHub リポジトリに接続する
4. CSV を読み込み、生データのままでは使えないことを確認する

4 つめが地味ですが大事なところです。届いたデータには、そのままでは集計に使えない行が混ざっています。それを目で見てから第 2 章のクレンジングに進みます。

## 使うファイル

`sql/step1a_setup.sql`

第 0 章で作ったワークスペースの左側の一覧から、`sql` フォルダを開いて `step1a_setup.sql` を選びます。エディタに開いたら、上から順に実行していきます。

**コピーと貼り付けは必要ありません。** 書き換えも必要ありません。

### 実行のしかた

| やりたいこと | 操作 |
|---|---|
| 選んだ文だけ実行 | `Cmd + Return`（Windows は `Ctrl + Enter`） |
| ファイル全体を実行 | `Cmd + Shift + Return`（Windows は `Ctrl + Shift + Enter`） |

最初は 1 文ずつ、または章ごとに区切って実行し、結果を見ながら進めるのがおすすめです。

### 実行するロールとウェアハウス

エディタ右上の文脈セレクタで、ロールが `ACCOUNTADMIN` になっていることを確認してください。ウェアハウスはこのファイルの中で `USE WAREHOUSE` を実行するので、事前に選んでおく必要はありません。

自分のリポジトリに置き換えて実施したい場合は、`sql/step1a_setup.sql` の末尾に「非公開リポジトリを使う場合」の手順をコメントで書いてあります。

### ワークスペースと GIT REPOSITORY は別のものです

ここで混乱しやすいのですが、この章で作る `GIT REPOSITORY` は、第 0 章で作ったワークスペースとは**別の仕組み**です。

| 仕組み | 役割 | 誰が使うか |
|---|---|---|
| ワークスペース | 画面でファイルを開いて編集・実行する入れ物 | 人（画面から） |
| `GIT REPOSITORY` | SQL からリポジトリの中身を**ステージとして参照する**入れ物 | SQL（`COPY` などから） |

同じリポジトリを指していますが、用途が違います。このあと `data` フォルダの CSV を `COPY` で読み込むので、**SQL から参照できる `GIT REPOSITORY` が必要**になります。ワークスペースに CSV が見えているだけでは読み込めません。

### API 統合は公開リポジトリでも必要です

認証情報が不要になっても、`API INTEGRATION` は省略できません。

```sql
CREATE OR REPLACE API INTEGRATION BCAST_GIT_API
  API_PROVIDER = git_https_api
  API_ALLOWED_PREFIXES = ('https://github.com/sfc-gh-kenokizono')
  ENABLED = TRUE;
```

`API_ALLOWED_PREFIXES` は「このアカウントから外に出ていってよい先」の宣言です。ここに書いていないドメインには接続できません。外部との通信を管理者が宣言した先に限定できる、というのがこの仕組みの意図です。

### API INTEGRATION は INTEGRATIONS スキーマに入りません

名前が似ていますが、置かれる場所と役割が違います。

| オブジェクト | 置かれる場所 | 何のために使うか |
|---|---|---|
| `BCAST_GIT_API`（API INTEGRATION） | アカウント全体 | GitHubへの接続先を許可するための「通行許可証」🔑 |
| `INTEGRATIONS`スキーマ | `BCAST_VIEWING_HANDSON`データベース内 | Gitリポジトリと、取り込み用ファイルの置き場をまとめる「箱」📦 |

Step 0では、データベースを作る前に、アカウント全体へ通行許可証を作りました。
Step 1ではデータベースを作り、その中にGit関連のオブジェクトを整理する箱を作ります。

```text
Snowflakeアカウント
├─ BCAST_GIT_API                 GitHubへ接続してよい、という許可 🔑
└─ BCAST_VIEWING_HANDSON
   └─ INTEGRATIONS              Git関連のオブジェクトをまとめる箱 📦
      ├─ BCAST_REPO             GitHubリポジトリの参照
      └─ BCAST_RAW_STAGE        CSVを読み込む前の置き場
```

### Git リポジトリのステージからは直接読み込めません

リポジトリの中身はステージとして見えますが、そこから `COPY INTO` でテーブルに読み込むことは**できません**。次のエラーになります。

```
Unsupported feature 'Copy into table from Git Repository'.
```

Git リポジトリのステージは「コードを置く場所」であって、大量データを読み込む口ではない、という設計です。そこで `COPY FILES` でいったん内部ステージに移してから読み込みます。

```sql
CREATE OR REPLACE STAGE BCAST_RAW_STAGE;

COPY FILES
  INTO @BCAST_RAW_STAGE
  FROM @BCAST_REPO/branches/main/data/;
```

`COPY FILES` はウェアハウスを使わないサーバーレスの処理なので、数秒で終わります。実務でも、リポジトリで管理したい定義ファイルと、ステージに置きたいデータファイルは分けて考えることになります。

## セッション変数と IDENTIFIER()

自分自身にロールを付与するところで、セッション変数を使っています。

```sql
SET current_user_name = (SELECT CURRENT_USER());

-- 変数に何が入ったか確認する
SELECT $current_user_name AS "変数の中身";

GRANT ROLE BCAST_ENGINEER_ROLE TO USER IDENTIFIER($current_user_name);
```

`SET` で入れた値は、`$` を付けて参照します。**中身を確認する行を挟んでおくと、うまくいかないときに切り分けが早くなります。**

`IDENTIFIER()` は「文字列をオブジェクト名として扱う」という関数です。これを外すと、変数の中身ではなく `current_user_name` という名前のユーザーを探しにいってしまい、見つからずに失敗します。ユーザー名やテーブル名を変数で組み立てるときに必要になる書き方です。

## 層の分け方について

作成するスキーマは 5 つです。

| スキーマ | 役割 | 誰が触るか |
|---|---|---|
| `RAW` | 放送局から受け取った原本を、加工せず保管するため | パイプラインだけ |
| `STG` | 異常値や重複を除き、分析に使える形へ整えるため | パイプラインだけ |
| `INT` | ID の名寄せ、番組枠との結合、1 分単位への分解を行うため | パイプラインだけ |
| `MART` | リーチなどの指標を、AI やアプリへ提供するため | 利用者 |
| `INTEGRATIONS` | Gitリポジトリと、取り込み用ファイルの置き場をまとめるため | パイプラインだけ |

生データを含む層は限られた人だけが見られるようにし、集計済みの層は広く使えるようにします。この差は第 6 章で実際に確認します。

## GitHub との接続について

この教材は公開リポジトリなので、認証情報やシークレットは不要です。ただし、接続してよいURLを制限する `API INTEGRATION` は必要です。

```
API 統合（接続先の URL を許可する）
    ↑ 参照
Git リポジトリ（リポジトリの中身をステージとして扱えるようにする）
```

接続できたかどうかは次で確認できます。

```sql
LS @BCAST_VIEWING_HANDSON.INTEGRATIONS.BCAST_REPO/branches/main/data/;
```

CSV のファイル名が並べば成功です。

## 読み込みの確認

`COPY INTO` が終わったら件数を確認します。視聴区間の合計が 1,050,648 行になります。

局ごとに行数が違います。局の規模の差を表しているためです。

1行は、1台のTVが1つのチャンネルを見ていた連続区間です。ログがない時間は、そのTVを見ていない時間です。正常な区間では、同じ `COMMON_ID` の時間が別の局と重なることはありません。

```text
ログあり 📺  = TVを見ている
ログなし 📴  = TVを見ていない
別の局へ連続 = チャンネルを移動した
```

## 生データに混ざっている、計算を狂わせる行

スクリプトの最後にある 2 つのクエリで、届いたデータの状態を確認します。

### 1. 成立していない行が混ざっている

放送設備の不具合や再送によって、そのままでは計算に使えない行が混ざっています。

```
全行数              1,050,648
終了が開始より前          200
視聴が24時間を超える      148
重複した行                300
```

数えるのは、**混ざり方ごとに指標のずれ方が違う**からです。

| 混ざり方 | 件数 | このまま集計すると何が起きるか |
|---|---|---|
| 終了が開始より前 | 200 | `終了 - 開始` がマイナスになる。合計すると他の行を打ち消し、**全体の視聴時間が実際より短く**出る |
| 視聴が 24 時間を超える | 148 | 受信機がつけっぱなしで記録が切れなかった行。1 件で 1 日分以上を占め、**平均視聴時間が引き上げられる**。第 2 章で 1 分単位に分解すると、1 行が 1,440 行以上に膨らむ |
| 重複した行 | 300 | 同じ視聴が 2 回記録されている。リーチ（台数）は変わらないが、**視聴時間とインプレッションが多めに**出る |

3 つ目がいちばん厄介です。「台数は合っているのに接触回数だけ多い」という形でずれるため、リーチだけを見ていると気づけません。

全体に対する割合は 0.1 パーセント未満です。少ないので放置してよさそうに見えますが、平均や合計は極端な値に引っ張られるため、この数百行が数字を動かします。

この 648 行を除いた **1,050,000 行** が第 2 章のクレンジング後の行数になります。第 2 章で実際にその数字が出ることを確認します。

局ごとに個別のクレンジングを用意するのではなく、同じ定義でまとめて処理する形にします。

### 2. 一部の局のデータが届かない日がある

```
NETWORK_ID  視聴日        件数
NW01        2026-07-17    2,952
NW02        2026-07-17    2,502
NW04        2026-07-17    1,758
NW05        2026-07-17    1,458
```

`NW03` の 7 月 17 日の行がありません。5 つの局からデータを集める仕組みでは、どこか 1 局が遅れたり落ちたりすることが必ず起こります。そのときに全体を止めるのか、届いた分だけで表示を続けるのかは、設計上の判断になります。

## この章で使ったクレジット

```sql
SELECT
  QUERY_TYPE                                   AS "種別",
  COUNT(*)                                     AS "実行回数",
  ROUND(SUM(TOTAL_ELAPSED_TIME) / 1000, 1)     AS "合計秒数",
  ROUND(SUM(CREDITS_USED_CLOUD_SERVICES), 6)   AS "クラウドサービスのクレジット"
FROM SNOWFLAKE.ACCOUNT_USAGE.QUERY_HISTORY
WHERE WAREHOUSE_NAME = 'BCAST_HANDSON_WH'
  AND START_TIME >= DATEADD('hour', -1, CURRENT_TIMESTAMP())
GROUP BY QUERY_TYPE
ORDER BY 合計秒数 DESC;
```

`ACCOUNT_USAGE` の反映には少し時間がかかります。すぐに見たい場合は Snowsight の Monitoring からクエリ履歴を確認してください。
